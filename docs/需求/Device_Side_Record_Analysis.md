# 设备端录制点击事件实现方案探究

在 Android 设备端直接**录制原始触摸事件**并**转化为可执行脚本**是可行的，而且这也是以前按键精灵类软件的底层原理。不过随着安卓大版本更新，安全限制越来越严格。下面是几种可行路径及所需的权限/包分析。

## 方案一：基于 `getevent` 和 `sendevent` (系统底层节点 / 需要 ROOT 或 ADB Shell)

这是最原生、最硬核的方式。Android 内核将触摸屏等输入设备映射为了 `/dev/input/eventX` 文件。

### 原理

- **录制**：运行 `getevent -t /dev/input/eventX`，它会吐出十六进制的裸数据（坐标点阵、压力、时间戳）。
- **回放**：将录制下来的内容，按指定格式转换后，使用 `sendevent /dev/input/eventX type code value` 打回系统内核。

### 所需条件（核心卡壳点）

- **权限要求**：**必须具有对 `/dev/input/` 的读写权限**。
  - **普通真机应用 App**：绝对拿不到这个权限（除非设备已 **Root**，授予 App `su` 权限）。
  - **通过你的 ADB 工具（PC端）**：可行！因为 ADB Daemon 在设备端运行的身份是 `shell` 用户，对 input 设备是拥有权限的。可以在 PC 上跑 `adb shell getevent` 来捕捉，再写正则解析出坐标。
- **依赖包**：零依赖，直接调用系统内置命令。
- **难点限制**：各品牌手机的 `eventX` 编号、多点触控（MT）协议解析极为复杂和碎片化，并且 `sendevent` 速度极慢（它不仅是一条一条发，还没有批量接口），难以做到丝滑流畅。

## 方案二：基于 Android AccessibilityService (无障碍辅助服务)

这是目前市面上合法、免 Root 的“连点器”、“自动化助手”采用的主流技术。

### 原理

- **回放（下发点击）**：从 Android 7.0 (API 24) 开始，通过 `AccessibilityService.dispatchGesture()` API 可以向系统模拟手势（点击、滑动）。
- **录制（捕获事件）**：遗憾的是，无障碍服务**不能**全局捕获具体的坐标点（你不能监听到用户点了哪里，它主要给你发 UI View Node 被点击的事件，而不是屏幕抽象像素）。要实现“坐标录制”，你需要配合一个**全局悬浮窗全屏透明遮罩层 (Overlay)**。

### 录制流程构想：

当用户开启“录制模式”，App 弹出一个全屏尺寸但不可见的悬浮窗拦截所有的 `onTouchEvent`。拦截到坐标后记录下来，然后再将这个点击用 `dispatchGesture` （或临时穿透）再点给下层真实界面。

### 所需条件

- **权限要求**：
  - **开启无障碍服务权限 (AccessibilityService)** （必须用户手动去系统设置-无障碍里打开）。
  - **显示在其他应用上层权限 (SYSTEM_ALERT_WINDOW)** （用于弹出透明录制遮罩或悬浮控制面板）。
- **所需开发**：
  - 你必须用 Java/Kotlin 写一个 Android 端的配套 App (.apk)，将其装在手机上，你的 PC 端软件再通过 ADB 发送 Broadcast/Intent 与这个 App 通信。
  - 也就是说，需要额外开发一个配套的“录制/执行端” Android 应用。

## 方案三：基于 UiAutomator / Appium 底层服务 (开发者生态方案)

基于 Android 开发的测试框架提供的远程能力（不需要用户装 App，只需 ADB 环境）。这也是 `Airtest` 和 `Auto.js(Pro)` 的底层依靠之一。

### 原理

在手机端运行一个伪装的服务，例如 `uiautomator` (通过 `app_process` 启动) 开发一个驻留后台的 Java 进程（Server）。由于是由 ADB Shell 启动的进程，它具有注入事件的高级权限（类似方案一，但封装得极好）。

### 录制流程（结合 PC 端投屏）：

手机端其实很难“悄无声息”地在别人的 App 里记录下坐标。最好的方案是，你的 PC 软件集成类似 `Scrcpy` 投屏：

1. 用户在电脑上看到手机画面。
2. 他用鼠标在电脑上的画面上点。
3. 你的 PC 软件拦截了鼠标点击的相对坐标点（录制）。
4. 因为是用户在 PC 上点的，PC 就在列表里生成了一条对应的 ADB Touch 脚本。

### 所需条件 (以纯 UIAutomator Server 方案为例)

- **权限要求**：无需手机 Root。因为启动该进程的身份是 PC 传递过去的 ADB `shell` 身份。
- **依赖包 / 开发**：
  1. 需要用 Java 编写一个继承自 `UiAutomator` 监听 Socket 的 `.jar` 或 `.apk` (但没有 Activity)。
  2. 每次连接时用类似于 `adb shell uiautomator runtest xxx.jar` / `adb shell CLASSPATH=xxx /system/bin/app_process` 在设备里跑起来。

## 总结：该怎么做？

如果你希望由 **ADB桌面软件直接驱动，且保持零依赖、零 Root 门槛：**

1. **设备端原生态录制（不带悬浮窗不带系统APP）** 极其困难且兼容性差（因为你跨服抓取不到前台应用的 Touch X,Y）。
2. **正确的产品思路：【PC端界面生成 & 手机端单向执行】。**
   就是我们之前说的，在你的 React 界面提供一个类似于**“取色器 / 坐标获取器”**（比如搞个手机真机截图扔到左边，鼠标放上去就能知道坐标），用户手动编排“哪里点一下，等一秒，哪里刷一下”，生成一个列表。这是成本最低的。
3. **更终极的：结合 Scrcpy 画面投屏拦截。** 别人在界面的投屏画面点一下，你的前端就往剧本列表加一行 `tap x y`。录完之后，一把生成 `.sh` 用 `sh /data/local/tmp` 跑。不需要考虑在手机这个孤岛系统内部去录制和拦截。
